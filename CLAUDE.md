# CLAUDE.md

Guidance for Claude Code in this repository.

## Read first

- `DESIGN.md` -- the architecture and the reasons behind it; the source of truth for design decisions. Don't re-derive something it settles.
- `TODO.md` -- open issues, limitations and deferred ideas. Check it before starting on something that sounds new; it may be recorded there with context.
- `README.md` -- what an operator sees: setup, commands, configuration, API.

Where documentation goes:

- `README.md`: minimal, for the people who run the service.
- `DESIGN.md`: concepts and mechanisms -- what something is for, where it is configured, which module handles it.
- The code and data files: the in-depth description -- a YAML file's syntax in its header, a module's reasoning in its docstring -- without repeating the general concepts from `DESIGN.md`.
- `TODO.md`: what is open. When an item is done, remove it, and update `DESIGN.md` if the design changed.

Documentation and comments describe the system as it is. No history ("changed on ...", "was ... before"), no references to earlier versions; git has the history.

## Commands

Host-side:

```sh
sh app/scripts/test.sh              # the whole suite + ruff, in docker-compose.test.yml (needs the dev stack's postgres)
sh app/scripts/test.sh -k geometry  # pytest arguments are passed through
sh app/scripts/gen_model.sh         # regenerate model/generated/ from the hand-written model files
                                    # (needs python3 + PyYAML; downloads the iD and OpenMapTiles sources
                                    #  into tools/.cache on first run)
```

The dev stack is `docker-compose.local.yml`: PostGIS on 127.0.0.1:7778, pgbouncer in front of it, and the app with `app/` bind-mounted, configured from `config.local/`. Names and ports (`-03`, 8003/8004/7778) are chosen not to collide with other stacks on the machine.

```sh
docker compose -f docker-compose.local.yml up -d
docker compose -f docker-compose.local.yml exec app python tools/manage.py import li
docker compose -f docker-compose.local.yml exec app python tools/manage.py compile-styles li
```

The dev server is http://localhost:8003, the devtools viewer http://localhost:8003/devtools; `--profile caddy` adds Caddy on http://localhost:8004. `manage.py` subcommands: `init-elevation` (once, the contour lines into the schema `elevation`), `import <area>`, `compile-styles [<area>]`, `pre-cache [<area>] [--fast] [--force]`, `drop-cache [<area>]`; an area defaults to `serve_area`. None of them empties the tile cache as a side effect.

Areas: `li` (Liechtenstein, imports in under a minute -- the one to develop with), `de_sh` (Schleswig-Holstein, the test and profiling area), `de_nb` (Niederbayern, hill country: the contour test area; `li` lies outside the elevation data), `de_nrw`, `de`. Verify on the dev stack with `li`; never test or poll the production server.

`app/tools/gen_classifier.py`, `rule_stats.py`, `profile_render.py`, `profile_search.py` and `measure_reprojection.py` are standalone scripts; each documents its invocation in its module docstring -- read it rather than guessing flags. The profilers are stdlib/`mapnik`/`psycopg2` only, with no `app.*` imports. Baseline profiles go into `profiles/`.

Deployment and server operation (`deploy.sh`, `manage.sh`, `publish.sh`) are in `README.md` and `DESIGN.md` "Deployment". Don't deploy, publish or touch the server unless asked.

## Architecture in brief

`app/` is mounted as `/app` with `PYTHONPATH=/app`, so its subdirectories are top-level packages; `app` itself is never imported. Entry points: `uvicorn web.main:app` and `python tools/manage.py`. Everything that outlives a container is under `/data`.

- `importer/` -- the import; `tables.py` is the schema of record.
- `renderer/` -- styles to Mapnik XML, icons, queries, Map pool, cache, pre-cache, grids.
- `search/` -- the four modes, phrase rules, ranking, result shaping; `api.py` is what `web` calls.
- `web/` -- HTTP only: a route translates a request into a `renderer`/`search` call and back. `devtools/` is the viewer.
- `lib/` -- config layering, db connections, text normalisation (the importer and the query side must normalise alike; `test_text.py` freezes it).
- `model/` -- categories, classifier rules, importance, parameters, search rules. `model/generated/` is generated by `gen_model.sh` and never edited by hand: change the hand-written files or the generator and regenerate.
- `styles/` -- layers, classes, colors, details, icons, grids.
- `scripts/` -- host-side shell scripts, the one exception to "everything runs in the container". Anything with real logic belongs in Python.
- `tools/` -- `manage.py` (thin argparse over module functions; never touches the database or filesystem itself), generators, profilers.

Key decisions (details in `DESIGN.md`):

- Classes and categories are precomputed at import by one classifier shared by map and search; queries never read tags.
- A class's start zoom is written only in `styles/classes.yaml`. Moving it earlier needs a re-import, and `compile-styles` refuses until then.
- Each import writes its own schema `<area>_<yyyymmdd>_<hhmmss>`; the server serves the newest complete one of `serve_area`, or `force_schema`.
- The numbers the modules agree on live in `model/parameters.yaml`. Never write one into code or SQL as a literal.
- Credentials are only in `config/postgres.env` (production, git-ignored), reached through libpq's environment -- never in `app/config/options.yaml`, code, the image, a compose file or compiled Mapnik XML. `config.local/` is tracked and holds only the dev password.

## Tests

The database-backed tests skip with a reason when Postgres is not up; the ones that read real rows skip unless `li` is imported (`conftest.py`'s `db` and `small` fixtures).

Tests are the design record as much as the code is. Most exist because the failure they prevent is silent -- a map that renders the wrong thing, a query that returns the right rows by scanning the whole table. When a test's docstring explains what it caught, that is why it is worded that way; don't loosen it to make a change pass.

## Working conventions

- Write readable, clean code; prefer the simplest solution that works.
- Don't guess at unknown information (numbers, API shapes, external behaviour) -- find it in `DESIGN.md` or the source, or ask.
- Comments say *why*, and especially why something that looks wrong is right. If you remove a comment's subject, remove the comment; if you keep the subject, keep the reason.
- Module changes are profiled on `de_sh` with the two profilers, not only tested.

### Two traps specific to this stack

- **psycopg binds with `%(name)s`, so pg_trgm's `%` and `<%` operators must be written `%%` and `<%%`** in any SQL string that carries parameters. A single `%` raises `ProgrammingError: incomplete placeholder` only when that statement runs, which for a rarely taken path can be much later. `app/tests/test_rank.py` checks the search module's SQL for it.
- **A CTE without `MATERIALIZED` is not a fence.** Postgres inlines CTEs, so a `WHERE <expensive expression> >= x` on the outer query is pushed down into the base scan and evaluated over the whole table before the join that was meant to narrow it. Same rows, so nothing fails; it just costs the table. The search's scored CTEs are `MATERIALIZED` for this, and a test counts the subplan's `loops=` in the plan. The reverse also bites: a value the planner should see as a constant (the search view) must not be read from a CTE.
